FOUR REQUIRED AUTHORING WORKFLOWS

A. Reaction steps

Provide Add step → choose cupboard input → add/edit movement(s) → duplicate/reorder. Ordinary authoring must not require scripts or manual state machines.

Include the example routine:
push cupboard 1 → cupboard 2 throw-and-return;
push cupboard 4 → cupboard 3 throw-and-return;
a later press → two movements together.

Use native signed crossing, rearm/latch and counted events. Atomically consume each step’s routing eligibility, with generation/watermark handling so delayed presses cannot trigger a later step.

Consuming a press closes the step’s trigger route while keeping its Free/Return response active until explicit input Deactivate or owning scene End. Offer explicit after-press deactivation. Where a same-motor Move requires handoff from an input response, perform the scoped handoff as part of the authored reaction.

Reusing the same active input in a later step must not silently recapture its reference or reset its latch. Navigation is not activation. Default progression arms the next step after required reactions are accepted; an optional Wait for reactions uses finite successful completion.

B. Persistent Mapping cues

Support cue-owned Mapping and an existing Mapping used as an independent cue instance. Reuse native components/editors. Snapshot the linked definition at Start; later edits affect later starts. Leave the original Mapping’s enabled state untouched.

Start evaluates current input once and processes normal changes. Mapping continues across cue navigation. Exact End closes output admission, rejects stale queued/in-flight requests at final dispatch, then performs scoped cleanup.

Expose cease-updates versus cease-and-end-owned-interactions. Motor mappings default to exact owned cleanup; any retained motor work remains visible/endable. Light cease-updates leaves its last value unless an authored reset/fade says otherwise.

Two cues may instantiate the same definition independently. Do not invent HTP merging or borrow/toggle a live shared Mapping. Include cupboard and fake MIDI-to-light examples.

C. Custom Behaviour packages

Deliver a working versioned package loader, generic parameter/alias inspector, SDK, and small finite and persistent examples.

Use stable package ID/version/hash, relative assets, declared I/O aliases and run snapshots. Loading, validation and editing are inert. Save packages/assets with the show.

Use the existing interpreter through a constrained host for trusted small programs. Document its actual language/API support. Serialize each engine’s execution; keep user callbacks off UI/audio/motor threads. Provide nonblocking host requests, clocks/timers, input snapshots, outcomes and explicit completion.

Validate ownership/generation at request acceptance and final dispatch. End closes admission, cancels timers/subscriptions and performs declarative owned cleanup even if a stop hook fails. Stale callbacks cannot reach a new run. Bound execution/queues and report errors; do not forcibly kill C++ threads or promise adversarial sandboxing.

Heavy/blocking libraries and video decoding may remain deferred. This does not defer working Custom Behaviour cues or their SDK.

D. Music scenes and Groups

Implement Timeline, Start First, Start First and Enter, Playlist, and Random, including nested ownership. Use the reviewed contracts and disclose intentional QLab differences. Timeline child continuation cannot double-schedule events. Random needs eligible no-repeat history and testable selection. Playlist motor progression uses finite success; indefinite work needs explicit Next/ending.

Finite Group success may leave persistent descendants active. Explicit Group End closes pending scheduling and ends only owned descendants/inputs, including retained work. It must not end independently launched work merely because its definition is nested in the Group.

One music Group contains a song with waveform, transport, tap markers, draggable/numeric action positions, zoom/snapping and the shared movement editor. Reuse native AudioLayer/Clip/TimeCue infrastructure through adapters. Editing movement duration does not ripple later song placements. Timeline offset/pre-wait in this view is one placement property, not two added delays.

Use one primary-song transport clock for scheduling and display, with explicit epoch/iteration identity. Dispatch on the coordinator, never in the audio callback. Do not run stock wall-clock triggers and the new schedule in parallel.
